Mukoko News · architecture

From a publisher's RSS feed to a card on a 3G phone

Three flows: how an article is ingested and enriched, how the app reads it, and how the feed was rebuilt around the pattern TikTok uses — no counting, no offsets, and nothing sent that the screen does not draw.

1 · Ingestion and enrichment

Two workers on two platforms. fly-worker in Johannesburg does all the fetching and never touches AI; fundi-news-enrichment does all the AI and never fetches a feed. They meet only in news.articles and in one notification.

2 · How the app reads

There is no API tier in the read path. Server Actions talk to MongoDB directly, and the gateway Worker — a separate product API for third parties and MCP — is touched by exactly one file in the frontend, for admin mutations.

3 · The feed, rebuilt on the TikTok pattern

The old feed paged by offset and computed a total. Both are habits from paginated search results, and both get more expensive the further a reader scrolls — on a feed where scrolling is the interaction. TikTok never counts and never offsets: it hands back a cursor and prefetches the next batch before you reach the end.

What changed, and why each one matters here

A cursor, not a page number

skip(n) re-walks and discards n rows server-side, so page 50 pays for pages 1–49 again. A keyset cursor names a position in the sort, so every page costs the same. It is also stable under insertion — on a news feed, articles land while you scroll, and offsets silently duplicate or skip them.

The tie-break lives in the filter, never the sort

Timestamps collide: 3,000 recent articles carry only 2,831 distinct datePublished values, so ~6% share one with another article. The cursor breaks ties on _id in the query filter. Putting _id in the sort key looks more correct and defeats the index — that variant did not finish inside 60 seconds, while the single-key sort streams as a merge.

Rank in the app, not in the database

"Top stories" sorted by qualityScore, which has no index — a blocking in-memory sort over the whole collection. Bounding it to 14 days did not help, because a window is still ~32,000 fat documents the sort must materialise. Reading the 200 most recent on the index and ranking those in JavaScript is 880 ms — and is what the rail means anyway, since "top stories" is the best of what is recent.

Send only what the card draws

Every feed item shipped the full article body and a 1024-float embedding, though article.content is read on the detail page alone. On a metered connection that is a bill someone pays. The list projection drops both — which also cuts the server-side fetch, since pulling fat documents off disk, not the index scan, was the actual cost.

Prefetch before the reader arrives

An IntersectionObserver with a 400 px root margin starts the next page while the current one is still on screen. On a fast connection it is invisible; on a slow one it is the difference between a feed that scrolls and a feed that stalls.

A failed rail degrades, it does not 500

Each section reads independently and falls back to empty with a banner above the content that did load. Previously one shared Promise.all with no catch meant a single slow query blanked the entire site — which is exactly what happened.

Where the pattern stops. The popular rail deliberately emits no cursor. There is no keyset over a ranking computed in application code, and handing back a cursor the read path would ignore sends the client to page one forever — it dedupes to nothing, still sees "more", and loops. Offset paging within a fixed pool is the honest answer for that one rail.
